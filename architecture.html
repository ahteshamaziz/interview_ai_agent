From single-purpose copilot to a modular career platform

A production path for splitting the backend from the Electron shell, hosting it centrally, and adding resume & job-hunting tools without a rewrite.

Prepared 24 Jul 2026 Scope backend extraction · hosting · desktop distribution · new tool modules Status proposal — awaiting go-ahead on Phase 1
Where this stands today

One Electron app, one backend, one machine

Right now the whole thing only works because everything lives on your laptop: the Electron shell talks to ws://localhost:8787 by name, the knowledge-base cache sits in a local MongoDB, screenshots land on local disk, and the Anthropic/Deepgram keys live in a backend/.env file next to the code that uses them.

That's the right shape for one tool on one machine. It stops being the right shape the moment you want a second machine, a second tool, or a second person using it — which is what you're asking for.

Decision
Modular monolith now — not literal microservices.

One backend deployment, organized as independent domain modules (auth, interview, resume, jobs) that share one process, one datastore connection pool, and one set of infra clients. Each module owns its routes and its data; none reach into another's internals.

Why not real microservices yet

You're one developer shipping four features. Separate services mean separate deploys, separate health checks, network calls where function calls used to be, and distributed-systems failure modes — paid for before you have the traffic or team size that justifies it.

Reconsider when

A specific module needs to scale, deploy, or fail independently of the others — e.g. resume PDF generation is CPU-heavy and blocking the interview WebSocket. Clean module boundaries now make that a lift-and-shift later, not a rewrite.

Before you host this publicly

Four things that are optional on localhost and mandatory in production

Auth + rate limits
Today, "only you can reach it" is the entire access control model. A hosted URL with no auth in front of it means anyone who finds it can burn your Anthropic and Deepgram quota. This has to land before or alongside the first deploy, not after.
Secrets off disk
backend/.env stays local-only. On the host, keys live in its secret manager (Railway/Fly/Render all have one) — never in the repo, never in a client bundle.
TLS everywhere
ws://localhost:8787 becomes wss://api.yourdomain.com. Electron's backendWsUrl needs to be a build-time/config value, not a hardcoded constant.
CORS allowlist
Once the React web app calls the API directly from a browser, lock cors() down to your actual origins instead of the open default.
Sequencing

Roadmap

Phase 1 — Extract & configure

Backend becomes host-agnostic

Split routes into domain routers under /api/v1/interview/*, move the WS URL and API base into Electron config instead of the hardcoded constant in preload.js, add a Dockerfile and health check. No new features — this is what makes every later step possible.

touches: backend/src/*, electron/preload.js, electron/main.js
Phase 2 — Ship it somewhere real

Deploy + lock the door

Stand up Railway + Atlas + R2, add auth and per-user rate limiting, point Electron at the hosted URL. This is the phase that turns "runs on my machine" into "runs for anyone."

new: auth module, rate limiter, storage client
Phase 3 — Package for other machines

Signed, auto-updating builds

Wire up electron-builder for macOS/Windows installers, code signing, and electron-updater so new machines just install once and stay current.

new: electron-builder config, CI build workflow
Phase 4 — New tools

Resume ATS score, resume builder, job hunting

Each ships as a new domain module behind the same auth and shared LLM/storage kernel — plus the React web app to use them from, since none need Electron's screen-capture access.

new: resume module, jobs module, apps/web
